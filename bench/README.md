# GTLang 解释器性能基准

用同一套算法对比 **gtc 解释器（Cranelift JIT）** 与 **Lua 5.4** / **Python 3.12**。
运行方式：`gtc --run <file.gt>`。

## 结果（Windows x64，release）

| 基准 | gtc JIT | gtc 原生(exe) | Lua 5.4 | Python 3.12 |
|---|---|---|---|---|
| 数组 1e8 次读 (`arr10.gt`) | 0.096s | 0.006s\* | 0.650s | 7.7s |
| LCG 1e7 次迭代 (`loop_lcg.gt`) | 0.044s | 0.035s | 0.262s | 2.4s |

\* 原生版 0.006s 是 LLVM 把常量数组求和折叠了（真实计算以 JIT 的 0.096s 为准）。

## 相对速度

- **gtc JIT vs Lua**：数组 **6.8×**，LCG **6.0×**
- **gtc JIT vs Python**：数组 **80×**，LCG **54×**
- **gtc 原生 vs Lua**：LCG **7.5×**

## 基准设计要点

纯函数 + 常量参数会被 Cranelift/LLVM **常量折叠**（如 `fib(35)` 编译期算完），
因此基准必须让输入**运行期不可知**：用 C 全局状态（LCG）、运行期读数组。
参见 `loop_lcg.gt`（每次迭代调用 C 更新全局状态，无法折叠）。

## 文件

- `arr10.gt` — 1e8 次数组读（10 元素数组 × 1e7 轮）
- `loop_lcg.gt` — 1e7 次 LCG 迭代（C 全局状态）
- `fib.gt` / `loop_sum.gt` / `array.gt` / `strcat.gt` — 其它基准
- `std2.gt` — 标准库功能演示

## 已实施的解释器优化

1. **Cranelift `opt_level=speed`** — 内联、常量传播、指令选择
2. **单次无符号比较**做数组边界检查（同时判负数与越界）
3. **常量/循环变量下标**的边界检查消除（JIT 与 codegen 双后端）

## 编译器/解释器**自身**的优化

- **运行时对象缓存**：内置 `gt_rt.c` 按内容哈希编译一次并缓存为 `.obj`，
  后续 `--c` 直接链接，不再重编译 C 运行时。
  实测 `--c` **0.49s → 0.13s（3.7×）**；集成测试 9s → 1.7s。
- 链接优先用 `-fuse-ld=lld`。

### 工具链自身耗时（2504 行程序）

| 操作 | 耗时 |
|---|---|
| `--check` | 0.016s |
| `--emit-llvm` | 0.004s |
| `--run` | 0.006s |
| `--c`（缓存后） | 0.094s / 2.5k 行 0.234s |

## 编译器/解释器**自身**的优化

- **运行时对象缓存**：内置 `gt_rt.c` 按内容哈希编译一次到 `%TEMP%\gtc\_rtcache\gt_rt_<hash>.obj`，
  后续 `--c` 直接链接该对象、不再重编译 C 运行时。
  实测 `--c`：**0.49s → 0.13s（3.7×）**；集成测试总时长 9s → 1.7s。
- 链接优先用 `-fuse-ld=lld`（LLVM 自带），失败才退回默认链接器。

### 工具链自身耗时（2504 行程序）

| 操作 | 耗时 |
|---|---|
| `--check`（词法/语法/语义） | 0.016s |
| `--emit-llvm` | 0.004s |
| `--run`（JIT 编译+执行） | 0.006s |
| `--c`（含运行时对象缓存） | 0.094s（小文件）/ 0.234s（2.5k 行） |
